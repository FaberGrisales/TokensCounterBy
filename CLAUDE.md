# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A terminal (TUI) app that visualizes the real cost/usage of **Claude Code** on this machine — a token usage visualizer, not a game, and not a client for calling any LLM API itself. It has four menu capabilities, all read-only: a live-refreshing monitor of local Claude Code session token/cost/context-window usage, a live-refreshing "Global Claude Usage" snapshot modeled on Claude Code's own `/usage` command, a read-only view of this project's configured MCP servers/hooks modeled on `/mcp` and `/hooks` (see https://code.claude.com/docs/en/costs, /mcp, /hooks) that also shows real local MCP tool-call counts and turn cost per server, and a per-subagent token/cost breakdown for one chosen session (exactly how much a single "Task" tool invocation consumed, not just the session-wide total). The app makes no network calls and needs no API keys — every number shown comes from parsing Claude Code's own local transcripts/config files on disk. There is no simulated/estimated-cost feature and no game mechanics (no wallet/credits, no call-history leaderboard, no pricing-editor screen, no CSV import). Model pricing (Claude only — see below) lives in `tokens_counter/models_config.json`, edited by hand. `tui.py` keeps one large ASCII-art title banner (`BANNER` in `render_header()`) by explicit user preference, but game/arcade-flavored copy elsewhere (menu naming, panel/table titles, status text) was deliberately rewritten to plain, direct language — e.g. no "transaction receipt"/coin imagery, no "cabinet"/"portal"/"transmitting signal" phrasing, no flanking-emoji marquee titles. Keep new UI text in that plain style rather than reintroducing game framing.

This app previously had a fourth menu option ("Call Live API") that made real metered calls to Claude/Gemini/Hugging Face/OpenAI (optionally with real Claude tool-use/MCP) and showed the real cost of that call. It was removed at the user's explicit request: it measured cost per test call, not the account-level usage the user actually wanted, and every remaining feature needs no API key at all. If similar functionality is ever requested again, `git log` has the full implementation (added, then removed, in the same session) to reference rather than re-deriving it from scratch.

## Commands

Run from the project root:

```bash
python3 -m venv .venv && source .venv/bin/activate   # create/activate a virtualenv (not committed to git)
pip install -r requirements.txt                      # install dependencies (just rich - see requirements.txt)
python3 start.py                                      # launch the interactive TUI app
python3 -m unittest tests.test_calculator             # run the full test suite
python3 -m unittest tests.test_calculator.TestSessionMonitor.test_get_all_sessions_includes_subagent_usage  # run a single test
```

There is no lint/format tooling configured in this repo.

## Architecture

**Entry point:** `start.py` adds the project root to `sys.path` and calls `tokens_counter.main.main()`. All interactive flow — the menu loop and dispatch to each feature — lives in `tokens_counter/main.py`. That file is the place to look first to understand how a menu option wires together config, pricing, and rendering. There is no persistence layer in this app (no database, no wallet state) — every menu action is a self-contained read of local state → render.

**Module responsibilities:**
- `config.py` — loads/saves `models_config.json` (pricing per Claude model, per-1M-token rates for input/output/cache-read/cache-write). `DEFAULT_CONFIG` is the factory fallback used on first run, and only ever contains Anthropic Claude models — the only provider whose model names can actually show up in Claude Code's own local transcripts, which is the only thing this app prices. `load_config()` also backfills: any model key present in `DEFAULT_CONFIG` but missing from an existing on-disk `models_config.json` gets merged in and saved, so adding a new default model to the code (e.g. a new Claude model Claude Code starts using) doesn't require existing users to manually edit their pricing file. `calculate_call_cost()` is the single source of truth for USD cost math: it treats `input_tokens` as the *total* input, then subtracts `cached_read_tokens` and `cached_write_tokens` from it to get standard-rate tokens, and applies each rate accordingly; it returns `0.0` for a model key with no entry in config (callers wanting an honest "unpriced" `None` instead check `model_key not in config_data` themselves before calling it — see `session_monitor.py`). Callers must pass token counts consistent with the "cached tokens already included in `input_tokens`" convention, not additive. There is no in-app UI to edit pricing — users edit `models_config.json` directly.
- `session_monitor.py` — reads Claude Code's own local session transcripts (JSONL files under `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<project>/<session-id>.jsonl`, plus any nested `<session-id>/subagents/**/*.jsonl` for spawned subagents/workflows) to show real, live, machine-wide token/cost usage per session — not just usage from this app. `find_session_groups()` pairs each top-level transcript with its nested subagent transcripts; `_iter_usage_lines()` extracts *only* token/model/timestamp metadata from assistant messages, deliberately never reading prompt/response text, and skips `model == "<synthetic>"` placeholder lines (zero-usage internal markers) so they don't inflate request counts. `build_session_summary()` buckets tokens by model (a session's main conversation and its subagents can use different models) into `by_model`, before pricing each bucket via `config.calculate_call_cost`, so cost is `None` (not `$0`) when a model has no entry in `models_config.json`. It also derives context-window usage from the *last* request only: `context_used_tokens` = that request's `input_tokens + cache_read_tokens + cache_write_tokens` (the full prompt size billed that turn — the best local proxy for "how much of the conversation currently occupies the context window", mirroring `/context`), divided by the model's `context_window` from `models_config.json` to get `context_percent` (both `None` if the model isn't priced). A session counts as active if its newest transcript file (main or any subagent) was modified within `ACTIVE_THRESHOLD_SECONDS` (300s). `watch_sessions()` drives a `rich.live.Live` loop calling `tui.render_session_monitor_view()` every few seconds until the user hits Ctrl+C. `build_subagent_breakdown()` is the per-subagent counterpart to `build_session_summary()`'s merged totals: for one session group it returns one row per subagent transcript file (not merged into the session total), reading token/cost the same way plus `_read_subagent_meta()`, which opens the sibling `<agent-id>.meta.json` Claude Code writes next to each subagent transcript for its `agentType` and a short one-line `description` (the same task label Claude Code's own transcript UI shows on a "Task" tool call) — never the subagent's actual prompt/response content, same invariant as `_iter_usage_lines()`. `get_subagent_breakdown(session_id, config_data)` looks up the matching group by `main.stem` and returns `(session_summary, breakdown_list)`, and `watch_subagent_breakdown()` drives a `Live` loop over it (like `watch_sessions()`) for `main.py`'s Option 4. `_iter_usage_lines()` also yields `tool_names`: the `name` field (only) of every `tool_use` content block in that assistant message — never the block's `input` arguments or any `tool_result` content, so it stays within the "usage metadata only" invariant. `_parse_mcp_tool_name()` splits an MCP tool's name (`"mcp__<server>__<tool>"`, splitting on the LAST `__` since server names can themselves contain underscores) into `(server, tool)`, returning `None` for non-MCP tool names like `"Bash"`. `get_mcp_tool_usage(config_data)` aggregates every local session's MCP `tool_use` calls by server: `total_calls`/`tools` (an exact per-tool call count) versus `turns`/token totals/`cost` (the cost of the *turns* that called that server at least once — Claude bills per turn, not per tool call, and one turn calling tools from two different servers gets counted under both, so this is deliberately labeled as a turn-level proxy, not a precise per-call cost, in both the function's docstring and `tui.render_mcp_tool_usage()`'s footer note — the same "state exactly what a number does and doesn't measure" pattern as `get_rolling_window_usage()`). `get_global_usage_summary()` re-aggregates every session's `by_model` bucket into one machine-wide "Usage by model" breakdown plus a per-project breakdown (grouped by `cwd` basename, falling back to the escaped project directory name) — the static counterpart to `watch_sessions()`, modeled on what Claude Code's own `/usage` command shows for a single session (see https://code.claude.com/docs/en/costs), but covering every local session at once. `get_rolling_window_usage()` re-scans every transcript line's timestamp (via `_parse_timestamp()`, which normalizes the trailing `Z` for `datetime.fromisoformat`) to sum real token/cost totals within rolling 5-hour and 7-day windows from `now` — the closest honest local analog to the consumption backing `/usage`'s plan-limit bars. It also tracks `window_start_at` per window (the OLDEST timestamp that currently still falls inside that window) and derives `elapsed_seconds` = `now - window_start_at` (capped at the window's duration) plus `percent_used` (`elapsed_seconds` as a % of the window's duration — a measure of how much of the window's timespan is occupied by continuous real activity, explicitly *not* a quota-used percentage) (all `None` when the window has zero activity right now — genuinely empty, not a guess). Two earlier versions got this wrong: the first tried to find a window "start" by treating the last local-activity gap >= the window's duration as a session boundary, which collapsed to "just started" after any ordinary multi-hour break; the second anchored to the *most recent* activity and counted down to when it would age out, which is mathematically sound but means every new request during an active session pushes the countdown back out toward the full window duration, so it visibly never decreases while the user is actively working. Anchoring to the *oldest surviving* activity instead fixes both: `window_start_at` doesn't move just because you sent another message, so `elapsed_seconds`/`percent_used` grow continuously with real elapsed time, and empty windows are reported as empty rather than papered over. Neither this nor anything else in the module can reproduce the plan-limit *percentage* `/usage` shows on subscription plans — that requires a live call to Anthropic's usage endpoint against an undocumented per-tier quota, and isn't cached to disk anywhere this app can read (checked `~/.claude.json`, `.credentials.json`, and `policy-limits.json` — none hold it). `watch_global_usage()` drives a `rich.live.Live` loop (like `watch_sessions()`) recomputing subscription status + both usage functions every few seconds and calling `tui.render_global_usage_live_view()`, so the Time-in-Window %/Time Elapsed numbers visibly tick forward instead of requiring the user to exit and re-enter the menu option; it imports `claude_config.get_subscription_status` lazily inside the function body to avoid a circular import, since `claude_config.py` itself imports from this module. This on-disk transcript layout is an internal Claude Code implementation detail (confirmed officially documented but explicitly not a stable API), so every parsing step degrades to "skip this line/file" on error rather than raising.
- `claude_config.py` — read-only reader for Claude Code's own local *configuration* (as opposed to `session_monitor.py`'s usage transcripts), modeled on the real `/mcp`, `/hooks`, and `/usage` commands. `get_mcp_servers()` reads project-scoped `<project_dir>/.mcp.json` plus user-scoped `~/.claude.json` (both its top-level `mcpServers` and its per-project `projects.<project_dir>.mcpServers` entry — note `~/.claude.json` is a file, not inside the `~/.claude/` directory, so it does *not* follow `CLAUDE_CONFIG_DIR`). `get_hooks_config()` reads `hooks` blocks from user `<CLAUDE_CONFIG_DIR or ~/.claude>/settings.json` and project `.claude/settings.json` / `.claude/settings.local.json`. `get_subscription_status()` reads plan/org/seat-tier metadata from `~/.claude.json`'s `oauthAccount` block and rate-limit-tier/subscription-type from `<CLAUDE_CONFIG_DIR or ~/.claude>/.credentials.json`'s `claudeAiOauth` block — it deliberately never touches the `accessToken`/`refreshToken` fields in either file, only the account metadata that sits alongside them, and returns `None` when there's no `oauthAccount` at all (e.g. this machine only uses an API key). None of the three cover organization-managed policy files (no confirmed stable path for those), and none can report the live 5h/weekly usage-limit percentages `/usage` shows — that data isn't cached to disk anywhere; it requires a live call to Anthropic's usage endpoint that only Claude Code itself makes. `get_mcp_servers()`/`get_hooks_config()` take an optional `project_dir` (defaults to `os.getcwd()`) purely so tests can point them at a temp directory instead of the real project.
- `tui.py` — all Rich-based rendering (banner, tables, panels). Pure presentation; takes plain dicts/rows from the other modules and has no business logic of its own. `render_subscription_status()` and `render_usage_summary()` build their panels/tables via `_build_subscription_status_renderables()`/`_build_usage_summary_renderables()` (private list-returning helpers) and then print them directly, for the one-shot case; `render_global_usage_live_view()` calls the same two builders but wraps the combined list in a `Group` instead of printing, for `watch_global_usage()`'s `Live` loop. `render_session_monitor_view()` and `render_subagent_breakdown_view()` follow the same "returns a `Group`" pattern, for `watch_sessions()` and `watch_subagent_breakdown()` respectively — the latter renders `None` `session_summary` (session removed between the picker list and this call) as a plain warning instead of a table. `render_claude_config()` and `render_mcp_tool_usage()` both just print directly (neither has a live-refresh counterpart) — `main.py`'s Option 3 calls them back-to-back, config listing first, then real local MCP call counts/turn cost below it.

**Data flow for a typical menu action:** `main.py` reads the choice → calls the matching `session_monitor`/`claude_config` function (which reads local files, computing cost via `config.calculate_call_cost` where relevant) → calls the matching `tui.render_*`/`watch_*` function to display the result. Nothing is persisted between runs, and nothing is fetched from any network. All four menu options are read-only views over Claude Code's own local state (transcripts via `session_monitor.py` for options 1, 2, and 4 plus the MCP-usage half of option 3, config files via `claude_config.py` for the rest of option 3) — options 1, 2, and 4 live-refresh via a `rich.live.Live` loop (`watch_sessions()`/`watch_global_usage()`/`watch_subagent_breakdown()`), option 3 is a static listing. Option 4 is two steps: `main.py` first prints a numbered picker of sessions that have at least one subagent (`session_monitor.get_all_sessions()` filtered on `subagent_count > 0`), then hands the chosen `session_id` to `watch_subagent_breakdown()`.

## Data and secrets

- `tokens_counter/models_config.json` is tracked in git (not gitignored), so `load_config()`'s auto-backfill of new default models (see `config.py` above) will leave real, committable pricing changes in the working tree.
- This app makes no external network calls and needs no API keys anywhere. If that ever changes again, keep reading real keys only from environment variables, never from a config file, and never write one to disk.
- `session_monitor.py` and `claude_config.py` read outside the repo, from `~/.claude` (or `$CLAUDE_CONFIG_DIR`), `~/.claude.json`, and the current project's `.mcp.json`/`.claude/settings*.json`, on the user's own machine. Keep all of that strictly read-only, and keep `session_monitor.py` extracting *only* usage metadata — never surface prompt/response text from those transcripts in `tui.render_session_monitor_view()`. This now includes `tool_use` block `name`s (for `get_mcp_tool_usage()`) — keep reading only the `name` field, never a tool_use block's `input` arguments or a `tool_result` block's content, both of which can carry arbitrary prompt-like data.
- `claude_config.get_subscription_status()` opens `.credentials.json`, which holds the user's live OAuth access/refresh tokens. It must keep reading *only* the non-secret fields alongside them (`rateLimitTier`, `subscriptionType`) — never extract, log, or render `accessToken`/`refreshToken`. Verify this invariant (e.g. via the existing `test_get_subscription_status_reads_account_and_credentials` test) before changing that function.
